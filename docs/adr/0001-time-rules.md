# Правила времени бронирования

Контекст: один заранее заданный владелец, гости без регистрации, бэкенд без базы данных. Решили: все правила времени считаются в таймзоне владельца `Europe/Moscow` (IANA, UTC+3, без перехода на летнее время с 2014 года); Booking window — 14 календарных дней, включая сегодня (`[today, today+13]`), скользит в 00:00 по Москве; рабочие дни — понедельник–пятница; Working hours — полуинтервал `[09:00, 18:00)`; старты привязаны к сетке от 09:00; Slot доступен, если его начало строго позже текущего момента, без буфера запаса; константы живут в Go-конфиге и отдаются фронтенду read-эндпоинтом, а не через env или дублирование на клиенте.

## Considered Options

- `Asia/Yekaterinburg` (пример из README) против `Europe/Moscow`: выбрали Москву как таймзону владельца; пример в README поправим в тикете контракта.
- Окно по рабочим дням (гарантированные 10 рабочих дней) против календарного: календарное проще и предсказуемее для гостя, выходные просто не имеют Slot.
- Границы часов включительно (`[09:00, 18:00]`) против полуинтервала: полуинтервал убирает неоднозначность слота «18:00–18:00».
- Константы в env против Go-конфига: env не добавляем, чтобы не расширять скоуп; инъекция конфига и часов даёт тестируемость.

## Consequences

- Бэкенд обязан считать сутки в `Europe/Moscow` независимо от таймзоны хоста; tzdata встроена через `time/tzdata`.
- Фронтенд не вычисляет доступность: только рисует константы и ответы `/available-slots`; `today` из конфига может протухнуть к полуночи, но сервер отклонит дату вне окна.
- Смена таймзоны, часов или рабочих дней — правка конфига и тестов, а не данных.
