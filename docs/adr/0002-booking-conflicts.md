# Занятость и конфликты при создании брони

Контекст: один владелец, гости без регистрации, in-memory хранилище. Решили: Booking занимает полуинтервал `[start_time, end_time)`, пересечение запрещено по всем типам встреч, примыкание разрешено; проверка занятости и вставка выполняются в одной критической секции booking store под `sync.RWMutex`; конфликт возвращается как `409 slot_taken`, невалидный слот — `400 invalid_slot`; hold и ключи идемпотентности не вводятся.

## Considered Options

- Проверка под `RLock` и вставка под `Lock` отдельными секциями: между ними возможна гонка, при которой два гостя получают один слот; отклонено в пользу одной критической секции.
- Hold слота на время заполнения формы: требует TTL, таймеров и фоновой очистки, расширяет scope; отклонено, потеря слота между показом и подтверждением — штатный путь.
- Ключи идемпотентности для повторной отправки: без авторизации и стабильного ключа запроса их неоткуда взять, а повторная бронь и так отсекается правилом занятости; отклонено, повтор возвращает `409`.
- Один глобальный мьютекс на всё приложение: связывает независимые коллекции; отклонено в пользу отдельного мьютекса броней.
- Отдельные коды для «в прошлом», «вне окна», «не на сетке»: действие UI одинаковое, причины уходят в `message`; отклонено в пользу одного `invalid_slot`.

## Consequences

- Хендлеры не берут мьютекс: стор возвращает `Booking` или типизированную ошибку, HTTP-слой только маппит её в статус и `ErrorResponse`.
- Повторная отправка того же запроса возвращает `409`; защита от двойного клика — блокировка кнопки на UI.
- Слот может исчезнуть между отдачей `/available-slots` и `POST /bookings`; UI обязан обрабатывать `409` обновлением списка.
- Предикат пересечения один для генерации слотов и создания брони, поэтому правила не расходятся.
- Тест на два параллельных запроса к одному слоту (`201` + `409`) обязателен.
